# Vespasian Formation, Figure Scale, And Bridge Modules Checklist

Snapshot: 2026-09-03

This is the authoritative implementation checklist for the coordinated Vespasian military-size, figure-scale, combat-data, Extractor DLL, and Load/Save DLL work. It supplements the stable contracts in `deep_refactor_requirements.md`, `object_owned_runtime_refactor.md`, `unit_and_formation_xml_plan.md`, `figure_owned_native_graphics_plan.md`, `renderer_scaling_seam_plan.md`, `runtime_dll_boundary_refactor_plan.md`, and `save_load_runtime_bridges.md`. When an older planning note conflicts with this checklist, preserve its compatibility invariants but follow the scope and gates recorded here.

Status legend: `[x]` verified baseline or completed work, `[ ]` pending, `[!]` known failing gate, `[-]` explicitly deferred.

## Scope And Non-Negotiable Outcomes

- [x] Change formation sizes, figure logical scale, and combat balance only through Vespasian data unless a shared engine correction is required to consume that data generically.
- [x] Preserve Julius behavior as Julius data declares it and bundled Augustus behavior as Augustus data declares it. A shared engine change must pass both lower-mod stacks without acquiring a Vespasian default, type-name branch, or compatibility fallback.
- [x] Keep all new unit combat values, formation capacities/layouts, graphics paths, logical sizes, and animation presentation data-owned.
- [x] Keep formation provenance engine-agnostic: Julius, Augustus, Vespasian, or any later mod may inherit, suppress, or replace enemy and herd definitions without executable-name or active-engine branches.
- [ ] Split Extractor and Load/Save into independently loaded, narrowly called, and unloaded DLL modules. Runtime must not retain pointers to DLL-owned memory or call module-private code after unload.
- [ ] Remove save-record knowledge from normal runtime. Records and record-version translations belong only to the Load/Save boundary; the running simulation owns live objects, modules, pointers/references, and typed indexes.
- [x] Keep old and recoverably inconsistent saves loadable. Every repair is diagnosed as a warning, canonical runtime relationships are rebuilt at load, the producer is corrected, and the next current-version save/reload is clean.
- [x] Fail loudly on invalid current XML, unresolved relationships that cannot be repaired, missing graphics, incomplete graphics composition, renderer compatibility fallback, DLL ABI/lifetime violations, and unallowlisted load/soak diagnostics.
- [x] Do not stage, copy, or author runtime-extracted Julius/Augustus pixels or generated `Group_*` trees under source `Mods`. Vespasian graphics XML may add authored semantics and logical presentation while referencing runtime-extracted lower-layer groups.

## Architecture Tenets

- Startup definitions are immutable typed objects. XML is the source of truth; startup resolves keys and relationships once, then runtime consumes the resulting objects.
- Mod composition is an ordered identity overlay, from the first configured layer to the last. A definition absent from an upper layer remains inherited; a definition with the same authored stable identity replaces the lower winner; a same-layer duplicate is invalid. Filenames are discovery paths, never registry identity unless the schema explicitly declares that path to be the identity.
- Completeness belongs to the final composed registry, not to each mod directory or XML file. A mod containing only `mod.xml`, or only a few replacement definitions, is valid when its complete dependency stack supplies the required final objects. Parsers stage every layer first, resolve winners, then publish and validate atomically.
- Whole-document resources follow the same rule at their natural identity boundary: declarative windows compose by `<window id>`, font families by `<family id>`, font surfaces by `<surface id>`, and localization by locale plus string/message key. Graphics retains its existing image-group composition semantics.
- Runtime relationships point to objects, not repeatedly resolved ids. A relationship owner publishes invalidation when it is removed, retargeted, disabled, or changes type, and every dependent unregisters or rebinds at that lifecycle event.
- Frequently queried classes self-publish into typed runtime indexes on creation or state entry and remove themselves on destruction or state exit. Callers query the narrow index instead of scanning all records and reconstructing membership.
- The composition direction is `WorldObject -> Figure/Building specialization -> composed Graphics, Housing, Rubble, Production, Storage, Formation, and other domain modules`.
- A runtime module binds one owner object, one immutable `*Def` pointer, and one mutable `*State`; behavior enters through the owner or its bound module.
- Save/load is a bridge, not a runtime model. It translates ids and record layouts into canonical live objects once and serializes those live objects back through an explicit export view.
- Major classes have matching `.h/.cpp` files. Headers list owned public and private methods; meaningful behavior should not disappear into anonymous static-helper islands.
- One-line behavior is inline where that improves navigation. Similar functions are consolidated into one well-shaped operation, and callers are migrated rather than preserved behind duplicate wrappers.
- Simple object-owned values need not acquire ceremonial accessors, but state that enforces registration, invalidation, clamping, relationship cleanup, or multi-field invariants remains private behind behavior methods.
- Every movable world object may own an exact fixed-point position and destination at 1/128-tile precision. Tile routing is only the coarse middle segment between those endpoints: changing movement modes must converge physically, never replace the rendered position, and final facing is applied only after exact arrival. Tile-only destinations are convenience projections into this same movement path, not a second movement system.
- Movement precision and render plane are independent properties. Exact/sub-tile ground movement remains in the ordinary tile painter order so buildings can occlude figures correctly; only explicitly elevated movement and temporary height adjustment enter the post-building elevated pass.
- Compatibility belongs at import/export boundaries. Runtime enum/string/id switches and silent fallback branches should shrink with every touched slice.
- Enemy and herd spawning is an explicit `FormationType` behavior, never inferred from figure-number ranges or a hardcoded one-animal-per-climate table. A definition with `<spawn role="enemy" />` owns one enemy figure archetype; `<spawn role="herd" climate="..." count="..." />` owns herd selection and initial count.
- A climate is allowed zero, one, or many active herd definitions. Zero means herd points create nothing; one is selected directly; many are selected deterministically from the active data set. No climate is required to contain a herd.
- Every live legion, enemy formation, and herd points to a resolved immutable `FormationType`. Missing definitions are fatal in normal runtime. The load bridge may repair a legacy identity only before publishing the canonical live formation.

## Historical Basis And Game Scale

- [x] Correct the terminology baseline: a Roman century was nominally about 80 men; an ordinary legionary cohort contained six centuries and was therefore about 480 men. English Heritage summarizes the six-by-80 organization in its [Hadrian's Wall teaching material](https://www.english-heritage.org.uk/siteassets/home/learn/teaching-resources/cross-curricular-learning/paid-like-a-roman-pages-91-94-hadrians-wall-teachers-kit-ks1-2.pdf), and the [Roman Inscriptions of Britain glossary](https://romaninscriptionsofbritain.org/reference/glossary) distinguishes the legionary cohort, auxiliary cohort, and cavalry turma.
- [x] Use 8x8, or 64 figures, as the Vespasian abstraction for a legionary century nominally about 80 men. The fort therefore represents a century-scale game unit, not a full roughly 480-man cohort.
- [x] Use 8x8, or 64 figures, for Vespasian auxiliary infantry, javelin, and archer century-scale formations. Auxiliary cohorts were also divided into centuries; equipment and battlefield role do not change the chosen square headcount abstraction.
- [x] Use a temporary square 6x6, or 36 figures, for the Vespasian mounted formation. A turma was about 30 cavalrymen, making 36 the closest practical square formation while mustering grounds remain square and only equal-sided rectangles are gameplay-validated. See the [RIB definition of `turma`](https://romaninscriptionsofbritain.org/reference/glossary); Alan Richardson's [Camps and Forts of Units and Formations of the Roman Army](https://doi.org/10.1111/1468-0092.00151) provides the broader fort-capacity context.
- [x] Record mixed-cohort evidence without implementing it in this slice. Segedunum describes a `cohors equitata` as about 480 infantry in six centuries plus 120 cavalry in four turmae, which scales exactly to 64 infantry plus 16 cavalry, or 80 figures. See [How were auxiliary units organised?](https://www.northeastmuseums.org.uk/segedunum/learning/how-were-auxiliary-units-organised).
- [x] Treat all totals as establishment approximations. The Flavian-period [Vindolanda strength report](https://romaninscriptionsofbritain.org/inscriptions/TabVindol154) records 752 total, 296 present, and 265 healthy for a nominally milliary cohort; detachments, illness, vacancies, and counting conventions make exact field strength variable.
- [x] Retain the direct Flavian uncertainty. [Josephus, Jewish War III](https://penelope.uchicago.edu/josephus/war-3.html) reports ten of Vespasian's cohorts at 1,000 infantry and thirteen at 600 infantry plus 120 cavalry. This is valuable period evidence but does not justify treating one ancient number as an exact universal roster.
- [-] Implement the future asymmetric `cohors equitata` as 64 infantry plus 16 cavalry only after mixed slot composition, asymmetric tactical layouts, fort mustering-ground presentation, recruitment, UI, and save behavior have their own accepted design.
- [-] Model a complete `ala quingenaria` at roughly 64 mounted figures only with a larger/asymmetric cavalry fort or another explicit representation. The current equal-footprint fort uses 36.
